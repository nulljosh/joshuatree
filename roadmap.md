Freestanding i386 kernel, no libc. v0 boots in QEMU with VGA text, PS/2
keyboard, RTC clock, and a shell that only knows `help clear echo time
reboot`. Everything below is the standard bare-metal-to-usable-OS path
(same order every OSDev-wiki "Bare Bones" -> "Meaty Skeleton" walkthrough
takes, and roughly what xv6/ToaruOS/Linux 0.01 did in their first months).

## v2, memory (from "one flat blob" to real address space)

Two real bugs, the kind this item was deferred to avoid rushing into. Page-directory entries and CR3 are walked by the MMU against physical memory, but every table is a higher-half C static whose own address is virtual; storing that virtual address into a PDE/CR3 pointed the MMU at unmapped garbage (instant page fault -> double fault, confirmed via QEMU's `-d int` trace). Fixed with a `phys()` helper subtracting the kernel's virtual base wherever a table's address is stored into another table or CR3. Second, found only because the regression suite includes real hardware: the RTL8139 NIC does raw physical-memory DMA with no concept of page tables, so handing it `(u32)rx_buffer` (now virtual) pointed it at the wrong physical location -- caught with a real `tcpdump` capture showing an all-zero frame, not by the shell's own (unaffected) MAC readout. Fixed the same way, a `KVIRT_TO_PHYS` subtraction at both DMA address registers in `rtl8139.c`.

Verified against every subsystem this kernel has (heap/task/ring-3/disk/graphics/network), including a real `tcpdump`-confirmed DNS+TCP+ARP round trip against the live internet.

## v3, multitasking (more than one thing running)

Preemption is real: a dedicated `preempttest` proves two never-yielding tasks both get real CPU time from the timer alone, verified three ways (raw counters, `MAX_TASKS` exhaustion behavior, and a full `tasktest`+`preempttest`+`sleep` run leaving the shell's output clean). One real regression this caught before shipping: `tasktest`'s demo tasks used to loop forever under the old cooperative-only model; bounded to 10 iterations then `hlt` so continuous preemption doesn't spam the shell forever.

Ring-3 (`ring3_test`) found two real bugs on the first attempt: the proof-of-execution marker was placed on an unmapped page (fixed by writing it into the already-mapped stack page, passed via register not symbol), and DS/ES/FS/GS aren't part of the CPU's automatic privilege-transition frame, so a ring-3 fault would otherwise resume the kernel's own handler with the wrong data selectors still loaded (fixed by forcing them back to the kernel selector at the top of every exception entry point in `isr.S`). No `int 0x80` gate yet at this point (that's v64).

## v6, graphics (text mode won't carry a browser), mostly done (Sep 2026), font renderer deferred
Runtime graphics on/off via QEMU's Bochs VBE register interface (ports 0x1CE/0x1CF), not the multiboot video-mode header (that boots QEMU straight into graphics with no way back to text). A capture-tool visual glitch right after closing a graphics window was chased as a possible register bug and ruled out: the kernel's real guest-visible text buffer was already correct the whole time (confirmed via keystroke-and-VGA-dump), the artifact is on the capture tool's side of the text/graphics transition, not a guest bug.

## Later hardware ideas: mic + camera input (Sep 2026)

## WiFi, real misconception corrected (Sep 2026)
This kernel's networking works through QEMU's emulated rtl8139 (a virtual *wired* NIC); `-net user` NATs that transparently through whatever real connection the host has, WiFi included, with zero WiFi-specific code anywhere. The host Mac's real WiFi chip is never exposed to the guest. Driver-level WiFi only becomes meaningful once this kernel targets real hardware with a real 802.11 card, and even then it's a large project on its own (chipset driver + WPA supplicant). Not started, not scoped for the emulator target at all.

## Absolute pointer / v62 / 0.60.0, a tap lands the cursor where the finger is (Sep 2026)
Every tap used to be relative (JS tracks a shadow cursor, paces PS/2 deltas), so the pointer visibly traveled. Real fix: the kernel now speaks the VMware absolute-pointer backdoor protocol (`drivers/vmmouse.c`, port 0x5658), wire format cross-checked against Linux's own `vmmouse.c`, QEMU's `hw/input/vmmouse.c`, and v86's vendored `libv86.js`. Premise correction: QEMU's cocoa display does speak this protocol too (`query-mice` reports it), not just v86. Three real "looks right, subtly wrong" traps found and fixed, each caught by a real artifact, not reasoning alone: (1) QEMU fakes a PS/2 dx=+1 event alongside every real backdoor packet just to raise the IRQ, so the driver has to discard stale PS/2 deltas once absolute mode is live or the cursor drifts one pixel right per host event; (2) a tap's press+release can land in the same poll and get coalesced into one drain, silently swallowing clicks -- fixed by never draining past a button transition; (3) a browser's synthesized mousedown/mouseup after a real touch doubled every tap into two press/release pairs -- fixed with `touchend.preventDefault()`. ## v63 / 0.60.1, dock hover root-caused: two real bugs, neither the one the recording suggested (Sep 2026)

The kernel's own animation state was NOT stuck (confirmed, ruling that theory out). Two real, separate bugs found instead: **(1)** the offscreen dock-band compose (v43's "draw once, present only changed slots" optimization) had been silently failing at 1920x1080 since it shipped -- `MAX_EXTRA_TABLES` (paging.c) was sized for one framebuffer, and at this resolution the LFB alone spans two 4MB page tables, leaving no room once kheap grows, so every hover fell back to a full on-screen repaint the whole time. ## v64 / 0.61.0, int 0x80 syscall gate, ring-3 tasks with a real lifecycle (Sep 2026)
The v28-deferred item and the "Accounts, passwords" prerequisite, shipped together. Before: `ring3_test` was a one-shot demo with no way to call into the kernel and no lifecycle; after, a ring-3 task is a real slot in `task.c`'s table, ending via `SYS_EXIT`, a CPU fault (reaped, kernel keeps running), or `task_kill`. ABI borrowed directly from x86 Linux (`eax`=number, `ebx`/`ecx`/`edx`=args, negative errno on failure, `__NR_exit`=1/`__NR_write`=4), exactly two real syscalls to start. `sys_write` validates every page of the caller's buffer via a new `paging_user_range_ok` (this kernel's `access_ok`) before touching it. Two real traps closed, both reasoned through against the Intel SDM before the first boot: `iret` to ring 3 silently nulls any of DS/ES/FS/GS still holding a more-privileged selector, so every task's saved frame now carries its own data-segment state; and one static TSS `esp0` can't serve two ring-3 tasks, so `schedule()` now repoints it per switch. A real, pre-existing kernel bug found along the way (not by reasoning, by a triple fault): `kheap.c`'s `grow_heap` never checked a newly-grown frame was physically contiguous with the old heap limit, so two interleaved allocations (a new task's stack, its page directory) could land on top of each other -- fixed by parking a non-contiguous stranded tail as its own free block and restarting the carve. This item is later named as the real trigger for what a 1.0.0 for this project would actually mean (see "Real direction: what 1.0.0 would mean" below). Honest gaps at ship time: only one user code/stack page exists (one ring-3 task at a time), `sys_write` is capped at 255 bytes, interrupts are off for the whole syscall.

## Multi-window, honestly scoped: what exists, what this pass shipped, what real windows still need (Sep 2026)
Before any of the phases below shipped: `drivers/window.c` was a framebuffer wrapper (one render target, one clip viewport, no window list, no z-order, no per-window backing store, no focus, no input routing), and every app was a blocking function polling the one global keyboard/mouse state. v67 (every app closes from its own X) and v69 (dock stays live, switches apps) were real prerequisites shipped ahead of this, neither is multi-window on its own. Since the bullets below were last touched: phase 3 batch 2 also shipped (v0.75.0, Reminders/Calendar/Mail converted too, see that entry below) -- 5 of 18 dock apps are now multi-window capable, and the "no double buffer" gap named in the compositor bullet below is the same root cause behind the keystroke-flash reports that keep recurring through v0.76.x (see "Real root cause for the still-reported flash" below). What real multi-window needs, in order:
- [ ] [Fable] **Window objects with backing stores in `drivers/window.c`.** A `struct window { x, y, w, h, title, z, focused, u32 *buf }` list, each window drawn into its OWN heap buffer, never straight into the framebuffer. Size is the real constraint: AA text is drawn at physical resolution (`window_pixel_phys`), so a backing store for today's 804x345 logical content rect at scale 2 is 1608x690x4 = 4.4MB; three windows is 13MB of a 32MB v86 guest, so either a smaller default window, logical-resolution stores with physical-res text re-rendered at compose time, or a per-window scale choice. Design call before code. Prior art with exactly this shape: ToaruOS's compositor (`yutani`, per-window shared-memory buffers composited in z-order), Haiku's `app_server`, and the OSDev wiki's "GUI" page; borrow the buffer-per-window + damage-rectangle model, don't invent one. **Phase 1 partial, v0.73.0 (Sep 2026)**: a real window list exists and two windows (Files, Weather) genuinely open/draw/close independently and simultaneously, see that entry below for the full real evidence -- but it lives in `kernel/kernel.c` next to the app-dispatch table it needs (not `drivers/window.c`, a deliberate deviation from this sketch, see that entry's reasoning), has no per-window backing store yet (both still draw straight into the shared framebuffer through the existing viewport clip, same as the old single-window model), and only 2 of the 18 apps are wired to it. **Phase 2, v0.74.0 (Sep 2026)**: real click-to-focus (clicking a visible background window raises it, `gui_multiwin_hit_test`) and real z-order compositing (`gui_multiwin_draw_all` and the hit test now share one list, so draw order and input agree) both shipped, see that entry below for the full real pixel evidence. The backing-store box above stays unchecked; that's still real, unstarted work for whichever future pass needs true per-window buffers (today's compositing is correct z-order over a shared framebuffer, not yet double-buffered/backing-stored), same for the 2-window cap and converting apps beyond Files/Weather off their blocking loop.
- [ ] [Fable] **A compositor in `gui_run`.** Desktop, then every window's store in z-order, then the pointer, with damage tracking so a keystroke in one window repaints that window's rect only. This kernel has no vsync and no double buffer (the v40/v45.1 tearing and flashing entries are exactly that pain), so the compositor also becomes the place a real back buffer finally lives; v41's `window_open_scaled` mode set is the only real cost model to test it against.
- [ ] [Fable] **Input routing by focus.** Today `kbd_pop`/`mouse_click_edge` are global and pulled by whichever loop is running. Multi-window needs a focused window (topmost under the last click), key events delivered only to it, click events hit-tested against the z-ordered list (chrome first: its X closes THAT window, its title bar drags it, then the content rect in that window's local coordinates). The v62 absolute pointer makes hit-testing trivial; the routing is the work.
- [ ] [Fable] **Apps stop blocking.** This is the big one and the honest reason it's multiple sessions, not one: 18 apps' loops have to become `open()` / `draw(win)` / `on_key(win, k)` / `on_click(win, x, y)` handlers over a per-app state struct so the compositor can interleave them, OR each app runs as its own kernel task (task.c already preempts, and v64 gave tasks a lifecycle) with the current viewport/target/AA-hook state in `window.c` made per-task and saved/restored on every context switch, plus per-task input queues the router fills. The handler conversion is the safer shape (no per-task draw-state hazard, no stack-per-window memory) and it staggers cleanly: the nine read-only `gui_launch_html` viewers plus Weather/Files/About share `gui_wait_close` and convert as one; Reminders/Trash/Settings/Calendar/Mail share the `sleep_ticks` + `get_key_or_click` list shape and convert as a second batch; Notes, Terminal, Keyrate, Chat each have a real bespoke loop and convert last, one at a time, each behind `appclose-check.py` extended to open two windows and close each from its own X.
- [ ] [Haiku] Once that exists, the two currently-unlit traffic lights (`gui_draw_app_titlebar`'s own comment says why they're unlit today: no windowing state to minimize or maximize into) become real, and the chrome's duplicate in-viewport title goes away.

Real estimate at the time phases above started: 3-5 sessions. Phases 1-3 (partial window list, click-to-focus/z-order, 3 more apps converted) are done; the compositor/backing-store/full-app-conversion boxes above are still real, unstarted work.

## v82 (0.68.2), reaptest root-caused and fixed, plus a real app-QA sweep (Sep 2026)

## Real root cause found: the browser demo's satellite wallpaper never worked end to end, and why (Sep 2026)
A saga spanning several passes, each real and each insufficient alone, finally closed. **The actual, final blocker**: `embed.js`'s `net_device: { relay_url: "fetch" }` mode makes every guest HTTP request a real browser `fetch()` from the page's own origin, and none of `ip-api.com`/`a.tile.opentopomap.org`/`mt0.google.com` send CORS headers -- a structural browser-enforced limitation for any deployment, not a sandbox fluke, confirmed by reading the real browser console (not just the kernel's own serial log). This is why the browser demo had never shown live network data end to end in any earlier pass; the kernel's own HTTP/DNS/wallpaper pipeline was always real and correctly proven via a real QEMU network stack (no `fetch()`, no CORS), just never exercisable through this specific browser-relay path. Fixed with a real, narrowly-scoped Cloudflare Worker proxy route (`worker.js`, `/api/proxy?url=`), using v86's own first-class `cors_proxy` option, hard-allowlisted to exactly the three real hosts this kernel's code ever asks for (hostname match, not substring -- rejects a lookalike like `evil-ip-api.com`). Verified locally via `wrangler dev` and, since this session's own sandbox couldn't reach the live URL either, via a `workflow_dispatch`-only GitHub Actions smoke test using the runner's own unrestricted internet -- real production evidence: all three hosts proxied correctly, real tile bytes returned (11157-byte PNG, 7685-byte JPEG, both `file`-confirmed as genuine images). ### Reframed: real hardware/userland limits, not bugs to fix
These read as simple asks but hit real architectural walls this kernel has by design. Noted honestly rather than silently built as something else:
- **WiFi drivers, Bluetooth, mic input, camera/selfies, battery/power/display controls, audio.** All need real hardware this kernel doesn't have a driver for yet (WiFi and Bluetooth need real chipsets; audio needs HDA/AC97; camera needs USB host controller + USB video class). This is exactly the existing "free OS, monetize on custom hardware" direction and the v100 voice north star's own prerequisite chain, not a new ask -- see those sections above. Meaningful once this kernel targets real hardware, not before.
- **Default Homebrew install + dotfiles.** Homebrew is a Ruby package manager built around macOS/Linux binaries, a POSIX shell, dynamic linking -- none of which exists here (flat binaries only, no dynamic linker). The honest equivalent is the native fetch-and-install tool queued above under P2.
- **Gaming support (Steam etc).** Steam needs OpenGL/Vulkan, a huge existing userland, and anti-cheat compatibility most real OSes struggle with. Off the table for a freestanding hobby kernel; not reframed, just out of scope.
- **Fully native drivers for real hardware.** Not a new item -- this is the existing, already-documented "free OS, monetize on custom hardware" direction. Real, large, ongoing, not a single task.
- **"Best of Kali/Ubuntu" apps and features.** Partially already true -- v30 already shipped real "basic hacking tools (Kali/Mr. Robot flavored)." Extend that existing set rather than starting a new "which distro to imitate" track.
