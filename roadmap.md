# Joshua Tree roadmap

Freestanding i386 kernel, no libc. v0 boots in QEMU with VGA text, PS/2
keyboard, RTC clock, and a shell that only knows `help clear echo time
reboot`. Everything below is the standard bare-metal-to-usable-OS path
(same order every OSDev-wiki "Bare Bones" -> "Meaty Skeleton" walkthrough
takes, and roughly what xv6/ToaruOS/Linux 0.01 did in their first months).

## v2, memory (from "one flat blob" to real address space)

  Two real bugs, not glossed over, each the specific kind this item was deferred to avoid rushing into. First: page directory entries and CR3 are read by the MMU itself, which only ever walks physical memory, but every one of these tables is now a normal higher-half-linked C static whose own address, as far as C code is concerned, is a high virtual one. Storing that virtual address straight into a page-directory entry pointed the MMU at physical memory that happened to be unmapped garbage, producing an instant page fault immediately escalating to a double fault, caught via QEMU's own `-d int` interrupt trace, not a guess (`v=0e` then `v=08`, same faulting EIP both times). Fixed with a `phys()` helper subtracting the kernel's virtual base everywhere a table's own address gets stored into another table or into CR3. Second, found only because the full regression suite included real hardware, not just the shell's own boot check: the RTL8139 NIC does raw physical-memory DMA, no concept of the CPU's page tables at all, so handing it `(u32)rx_buffer` (now a high virtual address) meant the card was reading and writing a physical location nowhere near the real buffer. The shell's own MAC-address readout still looked correct (that path goes through the CPU normally, via ordinary MMIO register reads), which is exactly the trap: `check.sh` and a superficial look would have called this shipped. A real `tcpdump` capture of the actual wire traffic caught it, an all-zero frame instead of a real ARP request. Fixed the same way, a `KVIRT_TO_PHYS` subtraction at both DMA address registers (`rtl8139.c`, which had already left itself a note anticipating exactly this).

  Verified against real artifacts across every subsystem this kernel has, not just a fresh boot: `check.sh`'s banner check; `heaptest`/`tasktest`/`preempttest`/`mem` (memory and scheduling untouched by the relocation); `ring3test`, including an independent QEMU-monitor read of the proof-of-execution marker at both its virtual and physical address, matching; a real FAT16 disk image exercising `disktest`, `mkdir`/`cd`/`ls`, and `cat`; `gfxtest` opening and cleanly closing graphics mode; and `nettest`'s full DNS+TCP+ARP round trip against the real internet, independently confirmed correct with a real `tcpdump` capture of the actual frames on the wire, not just what the shell printed about them.

## v3, multitasking (more than one thing running)

  A real regression this design would have shipped silently without catching: `tasktest`'s two demo tasks used to loop forever (`for(;;){puts("A");yield();}`), harmless under pure cooperative switching since they'd only ever run again if something explicitly called `yield()`. With the timer itself now driving rotation on every tick regardless of who calls what, those same infinite loops would have started spamming "A"/"B" onto the shell's own output every 10ms for the rest of the boot session, the first time anyone ran `tasktest`, forever. Fixed by bounding both demo tasks to their existing 10-iteration count then parking in `hlt` forever, silent and correct either way, not something spotted by `check.sh`, spotted by actually reasoning through what changes once every tick can reschedule.

  Verified for real, three ways, not just "boots": a dedicated `preempttest` command runs two tasks that call neither `yield()` nor `hlt`, incrementing plain counters, while the shell's own wait loop also never yields or halts on purpose, so if preemption weren't real neither counter could ever move. Booted headless and let it run for real wall-clock time (`ticks()`-based, ~200ms): both counters came back in the tens of millions, real, substantial CPU time handed to tasks that never asked for it. Second, ran the exact same check with all 6 task slots exhausted by `tasktest` beforehand: one counter incremented in the tens of millions and the other stayed exactly 0, which is not a random failure, it is the exact signature `MAX_TASKS` running out predicts (confirmed by checking `task_create`'s return value), real evidence the mechanism is working exactly as designed rather than coincidentally. Third, ran the full realistic sequence, `tasktest` then `preempttest` then `sleep`, and confirmed the shell's own text output stayed completely clean afterward, no stray "A"/"B" characters, proving the hlt-forever fix actually closes the regression described above rather than just sounding right.

  A real bug caught on the very first attempt, not glossed over: the payload's first version wrote its proof-of-execution marker to a plain C global by name, which the linker placed on a completely different page than the two pages actually marked user-accessible, faulting immediately with a page fault rather than ever reaching the intended privileged-instruction test. Fixed by moving the marker into the base of the already-mapped stack page instead of a third mapping, passed in via a register rather than referenced by symbol. A second real fix, not obvious until reasoning through it: DS/ES/FS/GS are not part of the CPU's automatic privilege-transition frame, so after a ring-3 fault the kernel's own exception handler would otherwise still be running with the ring-3 data selector loaded in those registers, harmless today only by accident of this GDT being flat (both data segments cover the same full 4GB), not by design; fixed by forcing them back to the kernel selector at the top of every CPU-exception entry point in `isr.S`.

  Verified three independent ways: the kernel's own exception handler correctly named and reported `general-protection`, not a crash or hang; a direct QEMU-monitor memory read of the marker's physical address, independent of anything the kernel itself claims, came back exactly `0xabcdef01`, proving the ring-3 code really executed before it faulted; and the existing `heaptest`/`tasktest`/`preempttest`/`mem` regression suite still passed unchanged afterward, confirming the new GDT/TSS/paging permission bits didn't disturb anything already working. `int 0x80` syscall gate not added yet, nothing calls into the kernel from ring 3 today to need one; add it once something does. Same one-shot caveat as the graphics command before its restore was fixed: `ring3test` halts the kernel by design when the fault handler halts (no process kill/reap exists yet, see `task.c`'s own note on the same gap), reboot afterward.

## v6, graphics (text mode won't carry a browser), mostly done (Sep 2026), font renderer deferred
A real fork discovered mid-implementation: requesting a video mode via the multiboot header (the obvious first approach) makes QEMU boot straight into graphics mode with no way back to VGA text, breaking the working shell until the font renderer exists too, since text and framebuffer output can't coexist that way. The better path is switching graphics on and off at runtime via QEMU's Bochs VBE register interface (ports 0x1CE/0x1CF), which needs the framebuffer's real physical address first, only PCI config space knows that, not a fixed constant.

  Real, honest complication found along the way and worth recording, not smoothed over: a `screendump`/`screencapture` of the screen right after closing a graphics window still showed a garbled vertical-stripe pattern even once the register restore was proven byte-for-byte correct. Chased that as a second possible bug (tried resetting Bochs's own leftover bank/virtual-width/virtual-height/offset registers too, on the theory a stale wide pitch was the cause) before the keystroke-and-VGA-memory-dump test above showed the kernel's actual guest-visible text buffer was already completely correct the whole time. Conclusion: the visual artifact is a capture-tool-side rendering glitch around the text-to-graphics-to-text transition, not a guest bug, and it did not reappear in this final build's own verification. Recorded here rather than claimed silently fixed, in case a real display someday reproduces it and this note saves the next person from re-diagnosing the register path that was already proven correct.
- [ ] [Haiku] Memory efficiency pass: this is a real standing constraint from here on, not a one-time task. Watch static allocations (paging.c's extra page tables, kheap's growth), avoid needless copies, keep the kernel's own footprint small before it starts hosting real app logic in v9. Revisit whenever a subsystem's memory use looks bigger than it needs to be, not just once

  First real instance of this: `kheap.c` never coalesced adjacent free blocks, a real documented gap, not a hypothetical one. Freeing two neighboring small buffers left two separate free blocks even though they sat right next to each other in memory, so a later request that would have fit their combined space, exactly the shape `chat`/`build`'s repeated allocate-a-buffer-then-free-it pattern produces, pulled in a whole new physical frame instead of reusing what was already free. Fixed by merging adjacent free blocks on every `kfree`, using a property already true of the allocator's own list order (each new block is carved at a higher address and pushed to the head, so consecutive list nodes are always memory-adjacent) rather than adding a separate address-sorted structure. Verified by proving the test discriminates, not just that it prints "ok": ran `heaptest`'s new coalescing check against the actual fix (`coalesced adjacent free blocks: ok`, and confirmed via `pmm_free_frames()` before/after that no new physical frame was pulled in), then temporarily reverted `kfree` to the old no-coalescing version and reran the identical test, which correctly failed (`coalesce failed`), before restoring the fix.

  v57 (0.57.0), second real instance, the other half of the same gap the coalescing fix's own `kheap.c` header comment already flagged (`ponytail: no splitting a larger free block on reuse`): reusing a free block handed the *whole* block to a request regardless of how much smaller the request was, whole-block-per-request. That's the mirror image of the coalescing bug, and the same real workload exposes it: `build`'s codegen path allocates one large scratch buffer, frees it, then several small per-app serve-response buffers run right after. Without splitting, the first small reuse of the freed scratch buffer ate the entire thing, so every small allocation after the first pulled in a fresh physical frame instead of reusing what was actually still free right next to it, the coalescing fix's whole point undone from the other direction. Fixed by carving a reused free block down to the requested size (plus header) whenever the leftover is worth its own header (`MIN_SPLIT_PAYLOAD`, 8 bytes), pushing the remainder back onto the free list in the block's old list slot; the remainder sits at the higher address (the tail of the original block), the shrunk block keeps the lower address, which is exactly the ordering the existing coalescing walk already assumes, so the two fixes compose correctly rather than fighting each other (confirmed: freeing both pieces afterward coalesces them straight back into one block of the original size, no lost or leaked bytes). Verified the same way as the coalescing fix, not just "prints ok": added a `heaptest` check (free a 200-byte block, take two 20-byte bites, assert the second lands within a header's width of the first, the one signature only possible if the leftover was actually carved into its own reusable block) and confirmed it fails correctly (`split failed`) when `kmalloc`'s split branch is temporarily removed, then passes (`split leftover reused: ok`) with the fix restored. Also measured directly with `pmm_free_frames()`: freeing a 3000-byte block then taking three 500-byte bites pulls zero new frames either way at that scale (the freed region already has slack in the current frame regardless of splitting), so that particular measurement doesn't discriminate the fix on its own, recorded honestly rather than cited as if it did; the address-adjacency `heaptest` check is the real discriminator and is what's kept in the permanent suite.

  Rest of this pass: looked at `paging.c`'s static tables for real oversizing, not just the ones already reasoned about in `kheap.c`'s own comments. `extra_page_tables[MAX_EXTRA_TABLES][1024]` (`MAX_EXTRA_TABLES` = 4) costs 16KB of static kernel memory for 16MB of mappable address space, a deliberate, already-tight ratio, not padding. `page_directory`/`first_page_table` are each the one page x86 paging requires, no slack to trim. Skimmed `kernel.c` for oversized stack buffers and unnecessary buffer-copies-where-a-pointer-would-do; nothing concrete turned up beyond small, already-tightly-sized scratch buffers (`char buf[12]`/`buf[16]`/`buf[32]`/`buf[64]` for number/hex formatting, a couple of `buf[2048]`/`buf[4096]` request/response buffers sized to their actual protocol use, not padding). Reporting that honestly rather than inventing a copy to eliminate that wasn't actually there: ponytail/YAGNI applies, this pass's one real, verified fix is the block-splitting gap above, not busywork.

Revisit once the font renderer and windowing surface have real content to arrange, not before there's anything to design. ## v10, talking to it like gato does (this is the actual point), done (Sep 2026)

  Chasing why the live curl-fetch of a generated page kept coming back empty turned into the most valuable bug of the session, not a wasted one: every network wait in this stack (`arp_resolve`, `dns_resolve`, `tcp_get`, `tcp_serve_once`) was a plain loop-iteration count, tuned by guessing how many empty polls a wait "should" need. That's fundamentally broken, proven by direct measurement rather than assumed: added a temporary debug print inside the wait loop and watched `ticks()` (the real PIT-driven counter from v1) genuinely advance the whole time, just at roughly 40/sec instead of the nominal 100/sec, because QEMU's own process wasn't getting scheduled by the host often enough to deliver its virtual timer interrupt on time under heavy host CPU load (a local LLM generating text, concurrent with other heavy work on the same machine). Not a kernel bug, an environment one, but the fix is real: every wait in `net.c` now checks `ticks()` against a real deadline instead of counting meaningless loop spins, with the budgets themselves widened to have margin for a loaded host (`LAN/WAN/SLOW_REPLY/SERVE_TIMEOUT_TICKS`). This is strictly more correct regardless of host load, not just a bigger number.

  Honest gap: under tonight's specific heavy host load, a full live curl round-trip against a `build`-generated page would need several real minutes per attempt with the widened budgets, too expensive to hammer repeatedly tonight. The generation and code-fence-stripping halves are confirmed real; the live serve-and-fetch half already worked earlier this session for `serveapp` (before this exact host-load spike) and rests on the exact same `tcp_serve_once`, so it is not a new, separately-broken path, just not re-confirmed live under tonight's specific conditions. Re-verify when the host isn't under unusual concurrent load.

## v12, voice mode: an LLM actually controlling this kernel, done (Sep 2026)
The v10 decision (voice stays a separate, gato-style host layer, no audio driver in the kernel) holds; this is that layer, one script, `tools/voice-control.sh`.

  Two real bugs, not glossed over. First: QEMU's monitor `sendkey` only accepts plain lowercase key names, an uppercase letter needs an explicit shift combo and most punctuation has no single-key name at all. The very first real test proved this the hard way: the LLM correctly answered "chat What is the capital of France?", but what actually landed in the kernel was "chat hat is the capital of rance", every capital and the question mark silently dropped. None of this kernel's commands need capitalization or punctuation to function, so the fix lowercases the LLM's command and strips anything that isn't a letter, digit, or space before typing it in, rather than mistype the answer into the kernel. Second, a plain prompt without examples mapped an open-ended question ("what's the capital of France") to the fallback "echo not supported" instead of the kernel's own `chat` command; fixed with a few-shot prompt showing that pattern explicitly, re-verified against four different spoken requests (a memory query, opening the GUI, a file listing, and an open-ended question) all mapping correctly afterward.

  Verified for real, twice over, end to end, not just the mapping step in isolation: since generating live human speech isn't something this session could do itself, used macOS's own `say` to synthesize real speech audio (a genuinely different, real signal, not a canned string), fed it through the real mic-recording-shaped pipeline. First run: synthesized "How much memory is free?" correctly became the kernel typing `mem` and printing the real, live frame count, confirmed by reading the kernel's actual VGA memory over the QEMU monitor, not by trusting the script's own printed claim. Second run, the more interesting one: synthesized "Ask the AI, what is the capital of France?" became the kernel typing `chat what is the capital of france`, which the kernel then ran for real, making its own separate network call to the same local Ollama server, and the real reply, "The capital of France is Paris.", appeared in the kernel's own VGA memory, an actual two-hop LLM chain (one model deciding what to run, a second one, inside the kernel, actually answering it), not a single call dressed up as two.

One event per date, not a list: a fresh add on a day that already has one overwrites its line in place (`cal_events_set`) rather than appending a second one for the same date, so both `EVENTS.TXT` and the dot/lookup logic stay single-entry-per-day; documenting that choice here since the task scope explicitly left it open.

`cal_date_str` builds the zero-padded `YYYY-MM-DD` string the file format and the grid's own lookup both key off of, same manual digit-building idiom as this file's own month title (`'0' + (vy / 1000) % 10`, ...) and `reminders.h`'s line-count formatting, no `sprintf`. The grid gained the one piece of real interaction it didn't have yet: a day cursor (`sel_d`, starting on today), moved with `[`/`]` rather than the arrow keys (already fully spent on month stepping, a real constraint the original task brief didn't account for, since v54 as actually shipped has no day-level selection at all to reuse, only month navigation). A light square renders behind the selected cell, independent of the "today" accent disc so both can show on the same day. Enter opens `cal_day_view`, a full-screen takeover-then-return view/add screen copied almost verbatim from `reminders_add_new`, pre-filling the edit line with that date's existing text if there is one. Changing month clamps `sel_d` into the new month's real day count instead of resetting to day 1 (so picking the 30th and stepping into a 28/29/30/31-day month still lands on a real day); `t` re-syncs `sel_d` to today the same way it already re-syncs `vy`/`vm`. Every day in the visible grid now also gets a small filled-dot indicator under its number when `cal_events_find` matches that day's `cal_date_str` against the loaded array, white when drawn over the "today" accent disc, clay-accent otherwise.

## v61 / 0.59.1, dock top-edge seam + diagonal ray aliasing, both root-caused (Sep 2026)
The two real defects left open from the entry above, both root-caused this pass with the boot-time direct-call trick (draw the desktop, halt before the event loop, `pmemsave` the real physical framebuffer under `-display none`, convert BGRA->PNG, inspect actual pixels), not guessed at from reading the code alone.

**(1) The top-edge seam.** `gui_rounded_rect_on_wallpaper` only ever blended toward the real wallpaper pixel in its four rounded-corner regions (`cx >= 0 && cy >= 0`); every straight edge, including the whole top edge between the corners (most of the tray's own width), fell through to a plain `col = color`, a 100% solid fill with a raw 1-physical-pixel cut straight into whatever was behind it, zero pixels of blend. That was never visible as "aliasing" in the usual sense, since a perfectly horizontal boundary has nothing to alias, but it read as a real seam anyway because of where the tray sits: a real framebuffer dump of the row immediately above the tray's top edge, well away from any corner (x=700/900/1100/1300, physical y=905-917) read `(2,0,1)`, `(9,5,4)`, `(1,0,0)`, `(4,2,3)`, i.e. genuinely near-black (confirmed this is the wallpaper's own darkest gradient row generally, not a dock-local bug, by sampling the same row far from the dock at x=50/200/1700/1850 and finding the same near-black values there too), landing directly against the tray's light cream fill (`0xEFEBE4`) one pixel later with nothing in between. That single-row jump from near-black to cream is what read as a "dark seam." The dock-band-cache/shadow's-first-row guesses in the entry above were both wrong: the band cache (`gui_redraw_dock_band`) is never even in the call path for a freshly booted static desktop (`gui_draw_desktop` calls `gui_draw_dock` directly), and the hand-drawn "soft shadow beneath the tray" only ever paints rows *below* the tray's bottom edge (`sy = y0 + dock_h + row`), nowhere near the top. Fixed: a new `else if (py < band)` branch in the same loop, mirroring the corner branch's own style, blends the outermost `band` (3 physical px, the same width the corners already use) rows of the straight top edge toward the real per-pixel wallpaper color via the same `gui_wallpaper_sample` the corners call, straight-line distance from the true edge instead of the corner arc's radial one. Real before/after pixel proof, same four x columns, physical rows 918-921 (the tray's own first four rows): before, `918=(239,235,228)` immediately (full solid, no transition); after, `918=(3,1,2)` (still background), `919=(83,80,78)`, `920=(161,158,153)`, `921=(239,235,228)` (full tray), a smooth 3-step fade essentially identical in shape to the exact gradient v58's own corner fix already produced and shipped (`1 -> 81 -> 160 -> 239`).

**(2) Diagonal ray aliasing.** Every capsule stroke in this file except one already scales its radius with the icon's own size (`gui_icon_notes`'s `s/11`, `gui_icon_terminal`'s `s/16`, etc.); `gui_icon_weather`'s eight sun rays were the one exception, a flat literal `2` no matter how big `s` (the supersample buffer size) got. The four axis-aligned rays (N/S/E/W) still looked crisp at that width, since a horizontal or vertical stroke's perpendicular offset from its own centerline lands the same way on every row or column it crosses, nothing to alias. Root cause: at `2` (supersample-space) radius, the diagonal rays are under one physical pixel wide even after downsampling, thin enough that no reasonable amount of box-filtering produces a consistent partial-coverage average along a 45-degree line, the same class of problem as a sub-pixel hairline. Fixed: a real `ray_r = s / 34` (with the original `2` kept only as a floor for however small an icon this might ever be asked to draw), proportional like every other stroke in this file, scaled up enough that the ray's total width clears the sub-pixel threshold that was actually causing the aliasing. Real before/after proof: a 160px direct render of `gui_icon_weather` before the fix shows the described sawtooth clearly on all four diagonal rays under 4x LANCZOS zoom; the identical render after the fix shows clean, smooth-edged diagonal rays matching the cardinal rays' own crispness; the real dock-size (post-hover-magnify) render shows the same improvement, diagonal rays now clearly resolved instead of reading as faint slivers against the burgundy background.

## v64 / 0.61.0, int 0x80 syscall gate, ring-3 tasks with a real lifecycle (Sep 2026)
The v28 deferred item and the "Accounts, passwords, real security" prerequisite, both `[Fable]`, shipped together since they were one change. Before: `ring3_test` was a one-shot ring-0 function that manually built an iret frame, dropped to ring 3, and the kernel halted for good on the payload's first fault; nothing could call into the kernel from ring 3 because no gate existed. After: a ring-3 task is a slot in `task.c`'s own table like any other, created by `task_create_user(entry, user_esp)`, and it ends one of three ways, every one of which returns the shell: `SYS_EXIT` through `int 0x80`, a CPU fault (reaped by `idt.c`, kernel keeps running), or `task_kill` from the shell.

The ABI (`kernel/syscall.h`, `kernel/syscall.c`, new) is x86 Linux's, borrowed not invented: `eax` = number, `ebx`/`ecx`/`edx` = arguments, result in `eax`, negative errno on failure, and the numbers are Linux i386's own (`__NR_exit` = 1, `__NR_write` = 4). Exactly two calls, the minimum that proves a round trip: `sys_exit(code)` records the status and goes through `task_exit_with`, the same free-stack-then-`int $32` path v28/v31 built; `sys_write(fd, buf, len)` copies from a user pointer to the console and serial, after `paging_user_range_ok` (new) has confirmed every page of `[buf, buf+len)` is actually mapped user-accessible, the same job Linux's `access_ok` does before `copy_from_user`, so a program can't hand the kernel a kernel address and have it echoed back. Dispatch is one table keyed by `eax` with null slots returning `-ENOSYS`, the `sys_call_table` shape. Nothing beyond that on purpose: no libc shim, no ELF loading, no wider surface.

`isr.S` grew `syscall_entry` (pusha, then DS/ES/FS/GS saved, kernel selectors loaded, `syscall_dispatch(frame *)`, everything restored, iret) and the 32 exception stubs were reshaped to the OSDev/James Molloy "push a dummy error code" form so `isr_handler(vector, err, eip, cs, eflags)` can read CS at a fixed slot. `idt.c` uses CS's RPL: ring 0 still reports and halts (a real kernel bug), ring 3 reports "ring-3 task hit general-protection (eip ...) -- task killed, kernel continues" and calls `task_exit_with(-vector)`. The gate is `0xEE` (present, DPL 3, interrupt gate): DPL 3 because with the exception gates' `0x8E` a user-mode `int $0x80` is itself a #GP, which would now look like a crashing program rather than a misconfigured gate; an interrupt gate rather than Linux's trap gate so IF is off for the whole handler, which makes `sys_exit`'s free-then-switch window safe by construction instead of by a `cli` it has to remember.

Two traps this tag exists for, both reasoned through against the Intel SDM before the first boot, neither visible in "it compiled": (1) `iret` to an outer privilege level silently nulls any of DS/ES/FS/GS still holding a selector more privileged than the new CPL, so a ring-3 task resumed by the timer with the kernel's `0x10` still loaded would #GP on its very next memory access. Fix: the four data segments are part of every task's saved frame now, pushed by `irq0`/every IRQ stub after `pusha` and popped before `popa` (`irq_stubs.S`), fabricated by `task_create_frame` (0x10 for ring 0, 0x23 for ring 3), the frame index `task_kill` patches moved from 8 to 12 (`F_EIP`). (2) One static TSS `esp0` can't serve two ring-3 tasks: the second's trap frame would land on top of the first's saved one. ## Multi-window, honestly scoped: what exists, what this pass shipped, what real windows still need (Sep 2026)
Direct request: "real windows, multiple apps open at once, each in its own window, each independently closable via its own X, not a single current-app model." Read `drivers/window.c` before assuming anything. What it actually provides today: one render-target abstraction (`window_pixel`/`window_rect`/`window_clear` at logical resolution over an s-times physical mode), one clip viewport (`window_set_viewport`, which is how v40+'s dock-launched app window works: the app draws full-screen coordinates and the viewport clips them into the chrome's content rect), one offscreen "screen band" for partial repaints, and one redirectable supersample target for icons. It is a framebuffer wrapper, not a window system: no window list, no z-order, no per-window backing store, no focus, no input routing. The chrome (traffic lights, title) is drawn once by `gui_launch_from_dock` straight into the framebuffer. And every app in this kernel is a blocking function with its own input loop (`gui_wait_close`, `get_key_or_click`, Notes' own loop, Terminal's, Keyrate's) polling the one global keyboard ring and the one global mouse state, returning only when it's done.

What this pass shipped toward it: v67 (every app closes from its own X, from the pointer alone, tested per app) and v69 (the dock stays live under an open window and switches apps). Both are prerequisites any windowing system would need first, both real and tested, neither is multi-window.

What real multi-window needs, in order, each a real step, none of them small, the reason it was NOT rushed into this same pass (the request explicitly preferred honest scope over a half-working system):
- [ ] [Fable] **Window objects with backing stores in `drivers/window.c`.** A `struct window { x, y, w, h, title, z, focused, u32 *buf }` list, each window drawn into its OWN heap buffer, never straight into the framebuffer. Size is the real constraint: AA text is drawn at physical resolution (`window_pixel_phys`), so a backing store for today's 804x345 logical content rect at scale 2 is 1608x690x4 = 4.4MB; three windows is 13MB of a 32MB v86 guest, so either a smaller default window, logical-resolution stores with physical-res text re-rendered at compose time, or a per-window scale choice. Design call before code. Prior art with exactly this shape: ToaruOS's compositor (`yutani`, per-window shared-memory buffers composited in z-order), Haiku's `app_server`, and the OSDev wiki's "GUI" page; borrow the buffer-per-window + damage-rectangle model, don't invent one.
- [ ] [Fable] **A compositor in `gui_run`.** Desktop, then every window's store in z-order, then the pointer, with damage tracking so a keystroke in one window repaints that window's rect only. This kernel has no vsync and no double buffer (the v40/v45.1 tearing and flashing entries are exactly that pain), so the compositor also becomes the place a real back buffer finally lives; v41's `window_open_scaled` mode set is the only real cost model to test it against.
- [ ] [Fable] **Input routing by focus.** Today `kbd_pop`/`mouse_click_edge` are global and pulled by whichever loop is running. Multi-window needs a focused window (topmost under the last click), key events delivered only to it, click events hit-tested against the z-ordered list (chrome first: its X closes THAT window, its title bar drags it, then the content rect in that window's local coordinates). The v62 absolute pointer makes hit-testing trivial; the routing is the work.
- [ ] [Fable] **Apps stop blocking.** This is the big one and the honest reason it's multiple sessions, not one: 18 apps' loops have to become `open()` / `draw(win)` / `on_key(win, k)` / `on_click(win, x, y)` handlers over a per-app state struct so the compositor can interleave them, OR each app runs as its own kernel task (task.c already preempts, and v64 gave tasks a lifecycle) with the current viewport/target/AA-hook state in `window.c` made per-task and saved/restored on every context switch, plus per-task input queues the router fills. The handler conversion is the safer shape (no per-task draw-state hazard, no stack-per-window memory) and it staggers cleanly: the nine read-only `gui_launch_html` viewers plus Weather/Files/About share `gui_wait_close` and convert as one; Reminders/Trash/Settings/Calendar/Mail share the `sleep_ticks` + `get_key_or_click` list shape and convert as a second batch; Notes, Terminal, Keyrate, Chat each have a real bespoke loop and convert last, one at a time, each behind `appclose-check.py` extended to open two windows and close each from its own X.
- [ ] [Haiku] Once that exists, the two currently-unlit traffic lights (`gui_draw_app_titlebar`'s own comment says why they're unlit today: no windowing state to minimize or maximize into) become real, and the chrome's duplicate in-viewport title goes away.

Estimate, active work: 3-5 sessions, in that order, each shippable on its own (backing stores + compositor first can land behind today's one-window behaviour with zero visible change, a real test being "the framebuffer is byte-identical to before"). Not started here. The freeze bug (v67) is fixed and shipped independently of all of this, as requested.

Every earlier caller (`web`, `weathertest`, `chat`, the old single-fetch `weather_fetch`) called `rtl8139_init` right before its one connection, resetting the ring and hiding this for sixty-odd versions. ## v73 / 0.65.2, the three pristine-v70 test failures, root-caused and fixed (Sep 2026)
Bounded QA pass, not open-ended bug hunting: v71's entry above logged three tests failing on pristine v70 HEAD, order-independent, never root-caused. All three now have real root causes, real fixes (or, for two of them, a real fix to the test itself once the production code turned out correct), and a real discrimination proof for each (temporarily broke the fix, confirmed the original failure text reproduced byte-for-byte, restored, confirmed green again).

**`calctest`, real bug, real fix.** `10/2 failed: got 0` traced to `kernel/calculator.h`'s `calc_unary`: it peeks one token ahead with `calc_next(lex)` to check for a unary minus, and on a miss rewound with a flat `lex->pos--`, undoing exactly one character. That's correct by accident for every 1-character token (a single digit, or any operator/paren), which is why "2+3", "2+3*4", "(2+3)*4" and "-2+3" (every number in them 1 digit) all passed and shipped clean in v70. It's wrong for a multi-character token: "10/2" tokenizes "10" as `NUM` with `num_val=10` and `lex->pos` left at 2 (just past it); `pos--` only rewinds to 1, so `calc_primary`'s re-lex starts mid-token at the lone `'0'` and reads `NUM 0` instead of `NUM 10`. `0 / 2` evaluates to exactly 0, the reported bug. Real fix: save the lexer's position before peeking and restore that exact saved value instead of assuming a 1-character step, so the rewind is correct regardless of the peeked token's width. `calc_term` and `calc_expr` had the identical peek-then-`pos--` shape for their own `+`/`-`/`*`/`/` lookaheads (not exercised by today's failure, since every boundary token there is a 1-char operator or `TOK_END`, but the same latent bug), fixed the same way for real correctness rather than leaving a second copy of a bug already found once. Discrimination proof: reverted `calc_unary`'s rewind back to the flat `pos--` alone, rebuilt clean, booted headless, `calctest` printed the exact original failure text (`10/2 failed: got 0`, `FAILED`); restored the save/restore fix, rebuilt, `calculator parser: ok`.

## v74 / 0.66.0, minimal PNG decoder, and the 4MB kernel-image cliff it uncovered (Sep 2026)
Queue item 1, "prerequisite bridge, part 1", done. `drivers/png.c` + `png.h`: 8-bit RGB (color type 2) and RGBA (type 6), non-interlaced, any number of IDAT chunks, ancillary chunks CRC-checked and skipped. Anything outside that (palette, grayscale, 16-bit, Adam7) returns `PNG_E_UNSUPPORTED` cleanly instead of misdecoding. Underneath: a real RFC 1950/1951 inflater, all three block kinds (stored, fixed Huffman, dynamic Huffman), canonical-Huffman decode in the zlib "puff" shape (count/symbol tables, no recursion, no large stack), plus RFC 2083's five scanline filters. Chunk CRC-32 and the zlib Adler-32 trailer are both verified. Output is one kmalloc'd buffer in exactly `wallpaper_rgb`'s layout (tight rows, top-down, R,G,B[,A]), so queue item 2 can hand a decoded tile straight to the wallpaper path.

**Verified pixel-for-pixel against a real host decode, not "it compiled".** `tools/gen_png_testdata.py` cuts three crops out of `drivers/wallpaper.h` and writes real PNG files by hand (not through PIL's encoder, on purpose): every scanline's filter type is chosen explicitly and cycled None/Sub/Up/Average/Paeth so all five reconstruction paths are provably hit, the zlib level is chosen per image so each DEFLATE block kind gets real coverage (320x180 RGB at level 9 = dynamic Huffman, 64x36 RGBA at level 0 = stored blocks, 6x5 RGB = fixed Huffman), and the block kind is read back out of the produced stream's header bits and asserted, not assumed. The IDAT stream is split across three chunks so the concatenation path is real too. The generator then decodes the exact bytes it embedded with PIL (the host-side reference decoder), asserts they equal the crop, and records an FNV-1a hash of the decoded bytes in `drivers/png_testdata.h`. In-kernel, `pngtest` decodes all three, compares every pixel to `wallpaper_rgb` at the crop's own offset (the expected pixels are the wallpaper itself, no second copy), hashes the output, and prints the hash on serial; `tools/png-check.sh` boots headless (`-display none`, the monitor `sendkey` path `regress.sh` already uses) and demands the kernel's hash equal the host's for each image. Result: `PASS: 3 images decoded in-kernel match the host decode byte-for-byte (rgb_dyn, rgba_stored, rgb_fixed), corruption rejected`. Two fault injections finish it: one flipped IDAT byte must fail on the chunk CRC (`PNG_E_CRC`), and the same flip with the CRC recomputed must still fail inside inflate/Adler-32 (`PNG_E_ZLIB`) rather than decode to garbage. A truncated file returns `PNG_E_TRUNCATED`.

**Discrimination proof, per 4b, on both harnesses.** Temporarily changed Paeth's tie rule (`pb <= pc` to `pb < pc`, the exact kind of off-by-one a filter implementation gets wrong): host harness reported 6046 mismatched pixels on the dynamic image and 108 on the RGBA one (hashes `8e2f6ec3` / `a325ba92` against the host's `74931e2a` / `7841b89b`), in-kernel `png-check.sh` failed with those same two wrong hashes; restored, both green again. The fixed-Huffman 6x5 image happened to stay correct with the broken tie rule (no tie occurred in 30 pixels), a useful reminder that the tiny image alone would not have caught it, the 320x180 one did.

**Real bug found underneath, not in the decoder: the kernel image crossed 4MB.** First boot with the fixtures linked in page-faulted right after `irq_install`, before `pngtest` could run. Root cause: `_kernel_end` went from `0x3f2000` (pristine HEAD, 56KB under the line) to `0x40f000`, and both the temporary map in `boot/boot.S` and the permanent one in `paging.c` covered exactly one 4MB page table (`paging.c`'s own comment: "add more page tables when something is allocated above 0x400000"). The first `.bss` write past 4MB hit unmapped memory. The 1.5MB baked wallpaper is most of the image; the PNG fixtures (~108KB of rodata) were just the straw. Fix, not a workaround: the base map is now two back-to-back tables (8MB) in both `boot.S` (2048-entry fill, PDEs 0/1 and 768/769) and `paging.c` (`BASE_MAP_TABLES`, `base_page_tables[2][1024]`), `IDENTITY_MAP_LIMIT` in `kheap.c` and `paging.c` moved to 8MB to match. A second latent bug came out of reading the same code: `paging_set_user` and `paging_user_range_ok` indexed the first table only, `(addr % 4MB) / 4K`, which silently flips the U/S bit on the wrong page for any address in the second 4MB; `ring3.c`'s user code/stack pages are static `.bss` arrays, exactly the class of data that just moved. Both now resolve the base table from the address (`base_table_index`, either alias). `PAGING_PRIVATE_PDE` is 2 (8MB), so the per-task private slot still sits just past the base map, no overlap. Shrinking the fixtures to squeak back under 4MB was considered and rejected: the next agent adding any static data would have hit the same cliff with a less obvious symptom.

**Verified for real.** `make kernel.elf` clean (same two pre-existing warnings as v71-v73), `./check.sh` PASS, `./tools/png-host-check.sh` PASS, `./tools/png-check.sh` PASS, `./tools/check-refs.sh` clean. The paging change is the risky part, so the whole task/ring-3/heap list was re-run from a fresh boot via v73's boot-time direct-call trick (temporary `kmain` detour, reverted before commit, `git diff` is the feature only): `heaptest` (reuse, coalesce, split leftover), `tasktest` (`ABABABABABABABABABAB`), `preempttest`, `ring3test` (int 0x80 write returned 31, exit 42), `ring3test fault` (GP at a ring-3 EIP, task killed, kernel continues), `killtest`, `isotest` (separate address spaces), `heapgrow` (past 0x400000, writable), all `ok`. Headless the entire pass, no `-display cocoa` window. `landing/v86/kernel.elf` re-synced with the new build. CI (`check.yml`, per 4d) gained both PNG steps and installs `python3-pil` for the generator. New tool `tools/shell-run.sh`: boot headless, type any shell commands, print the VGA screen and serial, the one-liner that surfaced queue item 10 above. ## v75 / 0.67.0, real map wallpaper of the real town, and the honest satellite finding (Sep 2026)
Queue item 2. The chain is now real end to end: `geo_fetch` (v71) gives the lat/lon, twelve map tiles come down over plain HTTP, `png_decode` (v74, extended here) turns them into pixels, and the desktop paints from them. Default on, the baked photo shows until the fetch lands and stays if it fails, never a blank desktop. Switchable in Settings (a third row, label says "Photo", the looked-up city name once the map is up, or "Map (fetching, photo until then)" while it isn't) and from the shell (`wallpaper photo|map|fetch`), persisted as `wall=` in `SETTINGS.TXT` exactly like `wind=`/`dock=`.

**The gate first, same standard as the Stocks-app check, real `curl` against every candidate before a line of code.** Forced 301 to HTTPS, unusable here: `tile.openstreetmap.org` and every OSM mirror subdomain, `tile.openstreetmap.de`, `openstreetmap.fr`, Esri World Imagery (`server`/`services.arcgisonline.com`), NASA GIBS (`gibs.earthdata.nasa.gov`, `gibs-a`), Stadia, terrestris WMS. Dead: `tiles.wmflabs.org`, `tile.stamen.com`, `map1.vis.earthdata.nasa.gov`. Real `200 image/*` on plain HTTP: Google `mt0.google.com/vt/lyrs=s` (satellite, JPEG), Bing `ecn.t0.tiles.virtualearth.net` (satellite, JPEG), CartoCDN basemaps (PNG), Thunderforest (PNG), OsmAnd's `tile.osmand.net/hd` (PNG, 512px), OpenTopoMap (PNG). So the honest answer to "satellite": the only satellite imagery that answers without TLS is JPEG, and this kernel has a PNG decoder only. Not faked: what shipped is a **map**, named as such everywhere (Settings row, shell, code), and a baseline JPEG decoder is now the one real prerequisite left for the satellite version, recorded in the queue below.

**Second real finding, invisible to curl, found on the first framebuffer dump.** CartoCDN and Thunderforest both answer keyless requests with a real, valid, full-size PNG that has a giant "API KEY REQUIRED carto.com/basemaps/apikey" watermark rendered diagonally across the tile (Carto's Fastly image layer does it; a `Referer` header doesn't help). The headers say 200, `image/png`, sane byte counts; only rendering it showed it. The first working build of this pass used Carto and put that watermark on the desktop, byte-for-byte correctly. OpenTopoMap (CC-BY-SA, free with attribution for light use, 256px tiles, 8-bit paletted, ~40KB each, no key, no User-Agent check, `Content-Length` and no chunked encoding on an HTTP/1.0 GET) is clean, and its topographic style (hillshade, contours, rivers) suits a desert-named OS better than a flat street map anyway. OsmAnd's tiles are clean too but it's an undocumented proxy for their own app, not a published service.

**Three real kernel gaps the chain exposed, each fixed at the root.** (1) `drivers/png.c` only did color types 2 and 6; every real plain-HTTP tile server serves color type 3 (indexed). Added PLTE parsing (1..256 entries, before IDAT, `PNG_E_FORMAT` if an indexed image has no palette or a sample indexes past it) and an RGB expansion on output, so the caller still gets `wallpaper_rgb`'s layout. (2) `http_get` used a `char raw[2048]` stack buffer for the whole reply, headers included; every body was silently capped at ~2KB, fine for the JSON one-liners it had served so far, hopeless for a tile. Now kmalloc'd at `body_maxlen + 2048`. (3) `tcp_get` used a fixed local port 44000 and ISN 0x1000 for every connection. Tiles 0, 1, 2 fetched and decoded fine, tile 3 failed at HTTP every run (`wallerr=http 3` on serial): the fourth SYN on an identical 4-tuple to the same server hit a connection SLIRP still held half-closed, since this side sends its FIN and, by design, never waits for the final ACK. Fresh ephemeral port per connection (44000..59999), ISN varied by it. Never bit before because every caller so far spoke to a different host once per boot.

**Tile math without libm.** OSM wiki "Slippy map tilenames": `x = (lon+180)/360 * 2^z`, `y = (1 - ln(tan(lat) + sec(lat)) / pi) / 2 * 2^z`. `ln`, `tan`, `sqrt` and `pi` come from the x87 directly (`fyl2x` with `fldln2`, `fptan`, `fsqrt`, `fldpi`, four one-line inline-asm helpers), the same FPU the calculator's doubles already run on. Zoom 12, a 4x3 mosaic (1024x768) whose top-left tile is `floor(x - 1.5), floor(y - 1.0)` so the town lands in the middle, then a 960x540 crop centered on it, clamped. Each tile is decoded and copied straight into the destination, never assembled into a full mosaic first: peak heap is the 1.5MB destination plus one decoded tile.

**How the rest of the desktop copes.** The two real readers (`gui_wallpaper_color`, `gui_wallpaper_row`) index a `wall_src` pointer instead of the array; `wall_apply` swaps it and drops the wind crown cache and the dock band cache so no frame is a stale composite of the old pixels. `gui_wind_shift` returns 0 on a map (streets don't sway) but the wind tick keeps running, because that tick is where v65's rain/snow particles are drawn; the day/night tint is untouched, it sits at the one choke point every wallpaper draw already funnels through.

**Verified for real, per 4b, all headless.** `tools/wallpaper-check.py` (new, permanent): boots with SLIRP, reads the `wall=z,tx,ty,cx,cy fnv` line the kernel mirrors to serial, recomputes the tile coordinates from the host's OWN ip-api answer (kernel `651,1403` = host `651,1403`), downloads the same twelve tiles, composes the identical crop with PIL and demands the FNV-1a of the finished 960x540 buffer match: `6b223a76` on both sides, byte-for-byte. Then pmemsaves the framebuffer and checks the wind band's mean color is the map tinted for the current hour (replicating `daynight_calc`), within 0.4 of the expected value and 126 away from the photo. Discrimination proved: with PLTE support reverted the kernel logs `wallerr=png -4` and the script fails; restored, it passes. `tools/wallfx-check.py` (new, permanent): escapes to the shell, forces rain through a new `weatherfx rain|snow|off` knob, `wallpaper fetch`, back into `gui`, dumps the screen: 169 pixels of the raw rain-streak color over the map with rain on, 0 with `weatherfx off`, and the band mean is still the tinted map (the 7:01 PM frame is visibly dusk-tinted against the 6:55 PM daylight one, real tint over real fetched pixels). `pngtest` and `tools/png-host-check.sh` gained a fourth fixture, `pal_dyn` (96x64, 40-color median-cut palette, dynamic Huffman, compared by host hash `0xca59e561` since its pixels are palette lookups) plus a "PLTE renamed away" fault case that must return `PNG_E_FORMAT`. `./check.sh` PASS, `tools/png-check.sh` PASS (4 images), `tools/geo-check.sh` PASS, `tools/check-refs.sh` clean. CI (4d): a new non-gating `network` job runs geo-check, wallpaper-check and wallfx-check for real on every push.
